## 1. 개요

### 배경

비디오 플랫폼에서 크리에이터가 새 비디오를 등록하면 해당 크리에이터를 구독한 회원에게 알림을 남겨야 한다. 비디오 저장과 메시지 발행을 분리하면 브로커 장애나 프로세스 중단 시 알림 이벤트가 유실되거나 중복 처리될 수 있다.

이 프로젝트는 Spring Boot, MySQL, RabbitMQ를 사용해 이러한 비동기 알림 흐름을 학습하고 검증하는 로컬 예제 애플리케이션이다.

### 목적

- 비디오 생성 트랜잭션 안에서 알림 발행용 Outbox 이벤트를 함께 저장한다.
- 저장된 이벤트를 RabbitMQ로 비동기 발행하고, 현재 구독자별 알림 이력을 남긴다.
- 재발행에도 수신자별 알림 이력이 중복 생성되지 않도록 한다.
- 발행·소비 실패를 재시도와 DLQ로 추적 가능하게 한다.

### 대상 사용자

| 사용자 | 필요 | 제공 가치 |
| --- | --- | --- |
| 백엔드 개발자 | 신뢰성 있는 비동기 알림 구현 방식 학습 | Outbox, publisher confirm, 멱등 소비를 한 흐름으로 확인 |
| 서비스 개발자 | 크리에이터 구독 관계 관리 | 회원 간 구독 생성과 취소를 HTTP API로 수행 |
| 운영·개발 담당자 | 로컬 시스템 상태 확인 | Actuator, Prometheus, Grafana와 RabbitMQ 관리 UI로 상태를 확인 |

### 범위

**포함한다.**

- 회원 생성과 조회.
- 회원 간 크리에이터 구독 생성과 취소.
- 크리에이터의 비디오 생성과 단건 조회.
- 비디오와 Outbox 이벤트의 원자적 저장.
- RabbitMQ 기반 비동기 알림 이력 생성.
- 중복 이벤트 수신 방지, 소비 재시도, DLQ 이동.
- 로컬 인프라와 메트릭 수집 환경.

**포함하지 않는다.**

- 사용자 인증·인가와 사용자별 권한 제어.
- 알림 이력 조회·읽음 처리 API.
- 이메일, 푸시, 웹소켓 등 외부 사용자 전달 채널.
- 비디오 수정·삭제·검색과 조회 수·좋아요 수 변경 기능.
- 운영 배포 환경과 다중 리전·다중 서비스 분리.

## 2. 목표와 성공 지표

### 제품 목표

1. 비디오 생성 시 알림 발행 대상 이벤트가 비디오 저장과 분리되지 않게 한다.
2. 크리에이터의 현재 구독자마다 하나의 알림 이력을 생성한다.
3. RabbitMQ 메시지가 재전달되어도 같은 이벤트와 수신자 조합의 알림은 하나만 유지한다.
4. 처리 실패를 재시도하고, 재시도 소진 메시지를 DLQ에서 확인할 수 있게 한다.

### 검증 가능한 지표

| 지표 | 성공 기준 | 확인 방법 |
| --- | --- | --- |
| 비디오 생성의 원자성 | 비디오가 생성되면 같은 트랜잭션에서 Outbox 이벤트가 저장됨 | 서비스·통합 테스트와 DB 확인 |
| 구독자별 알림 | 이벤트 처리 시 현재 구독자 수만큼 알림 이력이 생성됨 | RabbitMQ 통합 테스트 |
| 멱등성 | 같은 이벤트를 다시 발행해도 `(event_id, recipient_id)`별 이력은 한 건 | 재전달 통합 테스트 |
| 장애 격리 | 소비 실패는 설정된 재시도 후 `video.notification.dlq`로 이동 | RabbitMQ 설정 및 장애 시나리오 확인 |
| 비디오 생성 부하 기준 | k6 실행에서 실패율 1% 미만, p95 150ms 미만 | `k6/video-create.js` 실행 |

> 부하 기준은 현재 제공되는 로컬 k6 시나리오의 통과 조건이며, 운영 환경의 보편적 SLA를 의미하지 않는다.

## 3. 기능 요구사항

### P0. 회원 관리

**US-001. 회원 생성**

사용자로서 회원을 생성하고 싶다. 그래야 크리에이터 또는 구독자로 동작할 수 있다.

- `name`은 비어 있을 수 없다.
- 생성한 회원의 ID, 이름, 생성 시각을 반환한다.

**US-002. 회원 조회**

사용자로서 회원 목록과 단건 정보를 조회하고 싶다. 그래야 구독과 비디오 생성에 사용할 회원을 확인할 수 있다.

- 전체 회원 목록과 ID 기반 단건 조회를 지원한다.
- 존재하지 않는 회원은 `404 Not Found`를 반환한다.

### P0. 구독 관리

**US-003. 크리에이터 구독**

사용자로서 다른 회원을 크리에이터로 구독하고 싶다. 그래야 새 비디오 알림 대상이 될 수 있다.

- 구독자와 크리에이터는 서로 달라야 한다.
- 같은 구독 요청은 기존 구독을 반환하며 관계를 중복 저장하지 않는다.
- 구독자 또는 크리에이터가 없으면 `404 Not Found`를 반환한다.

**US-004. 구독 취소**

사용자로서 구독을 취소하고 싶다. 그래야 이후 생성되는 비디오의 알림 대상에서 제외된다.

- 같은 취소 요청을 반복해도 성공한다.
- 구독자와 크리에이터는 모두 존재해야 하며 서로 달라야 한다.

### P0. 비디오 생성과 알림

**US-005. 비디오 생성**

크리에이터로서 비디오를 등록하고 싶다. 그래야 구독자에게 새 비디오 사실이 비동기로 반영된다.

- `memberId`와 `title`은 필수다.
- 존재하는 작성자에 대해서만 비디오를 저장한다.
- 비디오 저장과 Outbox 이벤트 저장은 하나의 트랜잭션으로 처리한다.
- HTTP 응답은 비디오 생성 결과를 즉시 반환하며, 알림 이력 생성은 기다리지 않는다.

**US-006. 구독자별 알림 이력 생성**

시스템으로서 발행된 비디오 생성 이벤트를 처리하고 싶다. 그래야 이벤트 처리 시점에 크리에이터를 구독한 회원별 알림 이력을 남길 수 있다.

- 미발행 Outbox 이벤트를 주기적으로 RabbitMQ에 발행한다.
- broker confirm을 받은 이벤트만 발행 완료로 표시한다.
- 각 수신자에 대해 이벤트 ID와 수신자 ID 조합으로 이력을 한 번만 저장한다.

## 4. 비기능 요구사항

### 신뢰성

- RabbitMQ 발행 전 이벤트를 MySQL Outbox에 보관한다.
- publisher confirm을 받지 못하면 이벤트를 완료로 표시하지 않는다.
- 소비 중 런타임 오류는 재시도하며, 재시도 소진 메시지는 DLQ로 재발행한다.

### 관측성

- `/actuator/health`와 `/actuator/prometheus`를 노출한다.
- Prometheus는 애플리케이션 메트릭을 15초 간격으로 수집한다.
- Grafana는 시작 시 Prometheus 데이터 소스를 등록한다.
- Outbox 발행과 알림 소비의 배치·성공·실패·DLQ 이동을 로그로 남긴다.

### 보안과 운영 제약

- HTTP 요청의 필수 값은 Bean Validation으로 검증한다.
- 데이터베이스와 RabbitMQ 접속 정보는 환경 변수로 재정의할 수 있다.
- 체크인된 기본 계정은 로컬 개발용이며, 실제 자격 증명은 저장소에 커밋하지 않는다.

## 5. 제약사항과 가정

- 애플리케이션은 단일 Spring Boot 프로세스에서 API, Outbox 발행, 메시지 소비를 함께 실행한다.
- 알림 수신자는 이벤트를 소비하는 시점의 구독 관계로 조회한다.
- 알림은 데이터베이스 이력으로만 저장하며 최종 사용자에게 직접 전송하지 않는다.
- 로컬 통합 테스트와 실행에는 Docker가 필요하다.

## 6. 용어

| 용어 | 정의 |
| --- | --- |
| 크리에이터 | 비디오를 생성하는 회원 |
| 구독자 | 크리에이터를 구독한 회원 |
| Outbox 이벤트 | 비디오 생성 트랜잭션에서 함께 저장되는 RabbitMQ 발행 대기 레코드 |
| publisher confirm | RabbitMQ가 발행 메시지를 수락했음을 발행자에게 알리는 확인 |
| 멱등성 | 같은 이벤트를 반복 처리해도 결과가 중복되지 않는 성질 |
| DLQ | 재시도 소진 메시지를 보관하는 Dead Letter Queue |
